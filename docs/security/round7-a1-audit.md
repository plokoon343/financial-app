## Web, mobile and site (lighter pass)

- **XSS via unescaped user content:** one `dangerouslySetInnerHTML` found in the whole web app (finding 19, low risk, self-XSS only). No WebView or injected-HTML surface on mobile. React's own JSX text rendering (used everywhere else a transaction description/category/name is shown) auto-escapes by default.
- **IDOR in client-side routing/API calls:** the client never decides whose data it sees - every list/detail screen calls an endpoint scoped server-side by the authenticated user (see the Access Control section above). No client-side "pass an id in the URL and trust the server not to check" pattern found, because the server does check, everywhere.
- **Public website forms:** `/api/waitlist` and `/api/newsletter/subscribe` are both behind `authLimiter`. No separate unprotected "contact" form endpoint exists (the site's contact method is a `mailto:` link per the privacy policy, not a backend form). The corper campaign-code flow has no separate mutating public endpoint - codes are only consumed through the normal, rate-limited registration flow. `GET /api/public/promo` is read-only. Confirmed good.
- **Mobile deep-link / share-intent abuse:** see finding 13 above - both the in-app share-sheet and the native `QuietShareActivity` resolve the target account from the authenticated session or the capture key, never from the shared payload, so shared content cannot be used to write into a different account than the one that's actually configured.
